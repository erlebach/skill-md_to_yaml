## Summary

Phase 01.1 is a validation sprint: manually convert 5 representative HTML presentation decks to YAML DSL format, run them through `parse_deck_file()` + Pydantic validation, and fix any schema or parser bugs discovered. The goal is to prove DSL-01 ("Hybrid YAML+Markdown format") with real content before building the compiler in Phase 2.

The HTML decks live in `../n8n_to_python/output_html_files/` and were produced by a Claude-powered pipeline. They use a distinct CSS-based layout system (div classes like `two-col`, `card-grid`, `formula-block`, `step-list`) that does not map one-to-one to the 12 DSL layout types. The conversion task is authoring: a human (or Claude) reads each HTML slide and writes equivalent YAML DSL — not automated HTML parsing. The key research findings are which 5 decks to pick, what HTML features have no YAML equivalent (gaps), and what fixes may be needed to the existing schema/parser.

**Primary recommendation:** Select 5 decks that collectively exercise all 12 layout types. The best candidates are identified below. Conversion is manual/authoring work. Gap handling follows the CONTEXT.md decision: only add new layout types if content would be meaningfully lost; otherwise map to closest existing type.

## HTML-to-YAML Layout Mapping

### Patterns that map cleanly to existing DSL types

| HTML Pattern | CSS Class / Structure | Maps to DSL Layout |
|---|---|---|
| Opening section with `<h1>` and `<p class="lead">` | `slide-hero` or `slide--title` | `title` |
| Section opener within deck | `slide-hero` (mid-deck position) | `hero` |
| Standard content with bullets/paragraphs | `slide` (plain) | `content` |
| Full-bleed section separator | `slide--divider` | `divider` |
| Section with `<figure>` + raster image | `slide--figure` | `figure` |
| Section with inline SVG | `slide slide-with-diagram` or `slide--diagram` | `diagram` |
| Two-column div split | `two-col`, `two-col-nw`, `two-col-wide-narrow` | `two-column` (with appropriate proportion) |
| Python/code `<pre><code>` block | code inside `<pre>` | `code` |
| Numbered list | `step-list` or `<ol>` | `steps` |
| Closing/summary section | Last section pattern | `summary` |

### Patterns requiring judgment calls (potential gaps)

| HTML Pattern | CSS Class | Situation | Recommended Handling |
|---|---|---|---|
| Card grid | `card-grid` with 2-4 `<div class="card">` | Multi-card layout — no direct DSL type | Map to `content` or `comparison` with `<!-- split -->`. Cards are decorative; content is preserved as bullets/sections in Markdown body. Do NOT add new layout type. |
| Formula block | `<div class="formula-block">` with KaTeX `$$...$$` | Math formula within slide | Map to `content` — the `$$...$$` KaTeX syntax is valid Markdown body content and will render in Phase 2. No schema change needed. |
| Two-col narrow-wide | `two-col-nw` | Non-50/50 proportion | Map to `two-column` with `proportion: 40/60` or `60/40`. Already supported by schema. |
| Chapter label | `<div class="chapter-label">` | Deck 5 uses chapter labels above slide titles | No DSL equivalent — drop or include in `notes` field. Not significant content loss. |
| `<p style="...">` inline styles | Inline CSS on paragraphs | Custom styling (e.g., smaller font, color: var(--muted)) | Drop styling attributes; preserve text content in Markdown body. HTML-specific, no YAML equivalent. |
| Table inside slide | `<table>` with `<caption class="sr-only">` | Comparison table — most slides have one table | Map to `comparison` layout using Markdown table syntax in body with `<!-- split -->` if needed. Or `content` if table is informational. |
| Tag row | `<div class="tag-row"><span class="tag">` | Keyword tags on title slides | Drop or include as bullet list in body. Not significant content loss. |

### Known schema gap risk

**`TwoColumnSlide.left/right` type constraint:** `ColumnContent.type` is `Literal['figure', 'diagram']`. Real HTML two-column slides frequently have free text in BOTH columns (e.g., `two-col` with two `<div>` children each containing text and bullet points). The current schema handles this via the `body` field with `<!-- split -->` for text-only two-column layouts. This is sufficient — do NOT add `type: 'text'` to `ColumnContent` unless the test conversion reveals content loss.

### Pattern: Parametrized real-world validation test

```python
# tests/test_real_world_decks.py
import pytest
from pathlib import Path
from schema.parser import parse_deck_file

FIXTURES_DIR = Path(__file__).parent / 'fixtures'
REAL_WORLD_FIXTURES = sorted(FIXTURES_DIR.glob('real_*.yaml'))

@pytest.mark.parametrize('deck_path', REAL_WORLD_FIXTURES, ids=lambda p: p.stem)
def test_real_world_deck_parses(deck_path):
    """Every real-world YAML fixture must parse without errors."""
    deck = parse_deck_file(deck_path)
    assert len(deck.slides) > 0
    assert deck.metadata.title

@pytest.mark.parametrize('deck_path', REAL_WORLD_FIXTURES, ids=lambda p: p.stem)
def test_real_world_deck_has_no_unknown_layouts(deck_path):
    """All slides must use valid layout types (Pydantic validates this via AnySlide)."""
    deck = parse_deck_file(deck_path)
    # If parse succeeds, all layouts are valid — this test just documents intent
    for slide in deck.slides:
        assert slide.layout is not None
```

## Common Pitfalls

### Pitfall 1: Treating `card-grid` as a missing layout type

**What goes wrong:** The HTML decks use `<div class="card-grid">` for 2-4 card layouts. At first glance this looks like a missing layout type. Adding a new `card` layout would be premature.
**Why it happens:** The card-grid is a CSS presentation concern — the content (title + bullets per card) is fully representable as a `content` or `comparison` slide in Markdown.
**How to avoid:** Per CONTEXT.md decision: only add a new layout type if content would be meaningfully lost by mapping to an existing type. Cards are decorative; their text maps cleanly to bullets or `<!-- split -->`.

### Pitfall 2: The `body:` field in frontmatter error

**What goes wrong:** When writing YAML manually, it's tempting to write `body: |` followed by Markdown content inside the YAML block. This triggers a `ValueError` in the parser ("Field 'body' found in YAML frontmatter").
**How to avoid:** Always write the Markdown body BELOW the closing `---` of a slide's frontmatter. The parser handles the split.

### Pitfall 3: Inline SVG in YAML

**What goes wrong:** Real HTML decks embed full SVG source inline. The `diagram` layout type stores SVG via Mermaid syntax in the body, not raw SVG.
**How to avoid:** For slides with inline SVG, use `layout: diagram` with `alt_text` in the frontmatter and write a descriptive placeholder or Mermaid-equivalent in the body. Do NOT embed raw SVG — the schema has no `svg_source` field. This is expected Phase 2/3 territory (RICH-04).
**Warning sign:** If you find yourself pasting `<svg ...>` into a YAML file, stop and reconsider.

### Pitfall 4: KaTeX formula blocks

**What goes wrong:** Many HTML slides use `<div class="formula-block">` with `$$...$$` KaTeX syntax. This content maps to `content` layout with the formula in the Markdown body. The `$$...$$` syntax is valid raw text in the body field.
**How to avoid:** Use `layout: content` and include `$$...$$` blocks as-is in the Markdown body. The parser does not process KaTeX — it's preserved as text for the Phase 2 compiler.

### Pitfall 5: Proportion on two-column slides

**What goes wrong:** HTML uses `two-col-nw` and `two-col-wide-narrow` classes for unequal column proportions. The DSL `TwoColumnSlide` supports `proportion: '40/60'` and `'60/40'` but the default is `'50/50'`.
**How to avoid:** Set `proportion: '40/60'` explicitly for slides that use `two-col-nw`-style HTML. Don't leave it as the default 50/50 when the original was clearly unequal.

### Pitfall 6: Breaking existing tests when fixing schema

**What goes wrong:** If a schema change adds a new required field or changes a field name, existing fixtures (`valid_deck.yaml`, `two_column_variants.yaml`) may start failing their existing tests.
**How to avoid:** Run the full test suite (`pytest`) after every schema change. Update existing fixtures and tests to match the changed schema — but only update tests to match correct behavior, never to paper over bugs.

### Pitfall 7: `extra='forbid'` rejects unknown YAML keys

**What goes wrong:** All Pydantic models have `extra='forbid'`. If a manually authored YAML file includes an unrecognized field (typo, old field name), the parse fails with a validation error.
**How to avoid:** Validate each YAML fixture through `parse_deck_file()` early and fix errors immediately. Don't batch-write all 5 fixtures and then fix a pile of errors.

## Open Questions

1. **Inline SVG handling in `diagram` layout**
   - What we know: All 5 selected decks contain inline SVG embedded directly in HTML. The `DiagramSlide` body is intended for Mermaid source, not raw SVG.
   - What's unclear: Should real-world `diagram` fixtures include a Mermaid placeholder, or a textual description, or should SVG source be stored somewhere?
   - Recommendation: For this phase, write a descriptive placeholder in the body and note in the gap report. Phase 3 addresses RICH-04 (SVG embedding).

2. **Tables: `comparison` vs `content` layout**
   - What we know: Nearly every HTML deck has at least one comparison table. The `comparison` layout uses `<!-- split -->` in the body. Markdown table syntax is valid in any body field.
   - What's unclear: Whether Markdown tables in `content` body renders better than `comparison` with `<!-- split -->` for two-column table data.
   - Recommendation: Use `content` for tables with 3+ columns; use `comparison` for two-column comparison tables. Flag in gap report for Phase 2 compiler to handle.

3. **`chapter-label` div in Deck 5**
   - What we know: `clustering-ch8-prototype-tutorial` uses `<div class="chapter-label">` on every slide (e.g., "Data Mining — Chapter 8", "Section 1 — Fuzzy Clustering").
   - What's unclear: The DSL has `notes` (hidden) but no `subtitle` on `content`/`hero` slides.
   - Recommendation: Include chapter label text in the `notes` field, or drop it as a cosmetic HTML artifact. Document in gap report.
