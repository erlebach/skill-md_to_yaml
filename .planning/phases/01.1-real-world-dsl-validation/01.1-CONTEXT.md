**Gathered:** 2026-03-22

<domain>
## Phase Boundary

Validate that the Phase 1 DSL schema works correctly with real-world presentation content by converting 5 existing HTML decks to YAML DSL format. Catch schema gaps, parser bugs, and usability issues before building the compiler. Fix schema and parser issues discovered during validation. Close DSL-01 requirement.

</domain>

<decisions>
## Implementation Decisions

### Validation scope
- Convert 5 existing HTML decks from `../n8n_to_python/output_html_files/` to YAML DSL format
- Select decks with diverse content (images, diagrams, two-column, code blocks) to maximize layout type coverage
- Validation is both programmatic (parse_deck_file() + Pydantic) AND manual review for format usability
- A deck "passes" when: every slide parses without errors AND key content (titles, bullets, code, images) is faithfully represented in YAML

### Gap handling
- Fix schema and parser issues in this phase — don't defer to Phase 2
- When a real deck uses a pattern that doesn't fit the 12 layout types: add a new layout type only if mapping to the closest type would lose significant content or meaning. Don't add for cosmetic differences
- Update existing Phase 1 tests when schema changes are made, plus add new tests — but never write tests designed to make failures go away; tests must validate correctness

### DSL-01 closure
- This phase formally closes DSL-01 ("Hybrid YAML+Markdown format") — if 5 real decks parse successfully, the format is proven
- Mark DSL-01 as complete in REQUIREMENTS.md upon successful validation

### Test artifacts
- Converted YAML deck files go in `tests/fixtures/` alongside existing fixtures
- One pytest parametrized test that discovers all real-world YAML fixtures and validates each through parse_deck_file()
- Generate a Markdown gap report in `.planning/` listing: layouts used per deck, gaps found, schema changes made

### Claude's Discretion
- Which 5 decks to select from output_html_files/ (pick for layout diversity)
- Gap report format and level of detail
- How to handle HTML-specific features that have no YAML equivalent (e.g., inline styles, custom CSS)

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `parse_deck_file()` in schema/parser.py — validates full deck files, returns Deck object
- `TypeAdapter(AnySlide)` — validates individual slides via discriminated union
- Existing fixtures in tests/fixtures/ — patterns for how YAML decks should be structured

### Established Patterns
- Hybrid format: YAML frontmatter between `---` markers + Markdown body below
- `_looks_like_frontmatter()` heuristic distinguishes body text from next slide header
- `body` field excluded from JSON Schema (set via parser, not YAML)
- `extra='forbid'` on all models — unknown fields produce errors

### Integration Points
- New fixtures in tests/fixtures/ must follow existing naming conventions
- Any new layout types must be added to AnySlide union in models.py
- Parser changes must maintain backward compatibility with existing fixtures

</code_context>
